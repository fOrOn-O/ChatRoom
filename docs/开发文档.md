# ChatRoom 开发文档

> 版本：v1.1
>
> 更新日期：2026-08-20
>
> 文档定位：当前实现说明与架构指南

ChatRoom 是一个面向小型团队与社区场景的即时通讯项目。系统采用前后端分离架构：Go 服务端负责认证、业务接口、消息持久化与 WebSocket 连接管理；Vue 3 前端提供联系人、群组、实时消息和文件传输工作台。

本文档只描述仓库中已经存在的代码与可运行流程。产品演进方向统一放在文末路线图，避免将方案与现状混淆。

### 2.1 请求路径

普通 HTTP 请求经过以下链路：

~~~
浏览器
  → Gin 路由
  → CORS / 日志 / Recovery
  → JWT 鉴权（受保护接口）
  → Handler 参数校验与业务处理
  → GORM / MySQL
  → 统一 JSON 响应
~~~

实时消息走独立的 WebSocket 链路：

~~~
浏览器 WebSocket
  → JWT 鉴权
  → Upgrade
  → Client.ReadPump
  → Hub 私聊或群聊 Channel
  → 群聊按数据库当前有效成员解析接收者
  → MySQL 消息持久化
  → 目标 Client.Send
  → 发送者 chat_ack
  → Client.WritePump
~~~

### 2.2 组件职责

| 组件 | 职责 |
| --- | --- |
| Gin Router | 路由分组、公共中间件与鉴权边界 |
| Handler | 请求绑定、权限判断、数据库读写与响应组装 |
| Hub | 维护在线连接索引，串行处理注册、注销和消息路由；群聊以数据库当前有效成员为投递依据 |

## 4. 服务生命周期与并发模型

### 4.1 服务启动

服务入口位于 backend/cmd/server/main.go，启动顺序如下：

1. 读取配置并初始化日志。
2. 建立 MySQL 与 Redis 客户端。
3. 创建 Hub，并在独立 Goroutine 中运行 Hub 事件循环。
4. 创建 Gin 路由并启动 HTTP Server。
5. 监听 SIGINT 与 SIGTERM，通过带超时的 Shutdown 完成优雅关闭。

### 4.2 Client 读写分离

每个 WebSocket Client 启动两个 Goroutine：

| Goroutine | 责任 |
| --- | --- |
| ReadPump | 接收浏览器帧、解析并路由 chat 事件 |
| WritePump | 从 Send Channel 取消息、JSON 序列化、写入 WebSocket、定时 Ping |

这样可以保证单个慢连接不会阻塞其他连接的消息分发。Client 的发送缓冲区大小为 256；Hub 对慢消费者采用非阻塞投递策略，避免主循环被阻塞。

### 4.3 Hub 事件循环

Hub 持有以下 Channel：

| Channel | 作用 |
| --- | --- |
| register | 注册新的在线连接 |
| unregister | 清理断开的连接 |
| private | 路由单聊消息 |
| group | 路由群聊消息 |
| broadcast | 广播系统消息 |

Hub 的 Run 方法使用 select 串行消费这些事件。在线用户与群组连接索引使用 RWMutex 保护：写操作在注册、注销阶段进行；消息投递先在读锁内复制连接快照，再在锁外写入 Client 的发送缓冲区。缓冲区已满的慢连接会从 Hub 移除并关闭。

`SendPrivate`、`SendGroup` 和 `Broadcast` 使用非阻塞方式向 Hub 提交消息，并向调用方返回处理结果。Hub 已关闭时返回 `ErrHubClosed`，对应消息队列已满时返回 `ErrHubQueueFull`，不再只记录日志后静默丢弃。私聊或群聊提交失败时，消息不会进入持久化及投递流程，发送者会收到包含原始 `msg_id` 的 `error/1005`；广播提交失败则由调用方根据返回错误决定记录或重试。

群聊投递不再把连接建立时缓存的群组列表作为成员权限来源。每条群消息投递前都会从数据库查询正常群组中的有效成员，再将这些用户 ID 映射为当前在线连接。因此，在线用户退出或被移出群组后无需重连即可停止接收；新邀请的在线用户也无需重连即可开始接收。成员查询失败时采用失败关闭策略，不向缓存中的旧成员投递消息。

消息只有成功写入 MySQL 后才会投递并返回 `chat_ack`。写库失败时不会向接收者投递，发送者会收到带原始 `msg_id` 的 `error/1005`。群聊先解析当前有效成员再写库，避免成员查询失败的消息进入历史记录；私聊接收者离线时，消息仍保存在历史记录中并向发送者返回 ACK，不再维护重复的“离线消息存储”步骤。

`msg_id` 同时作为消息幂等键。同一发送者在当前权限校验通过后使用相同 `msg_id` 重试，并且接收目标、接收类型、内容类型和内容与历史记录完全一致时，服务端不会重复写库或再次实时投递，只返回 `chat_ack: sent`。如果相同 `msg_id` 对应的发送者、目标或内容不一致，服务端返回 `error/1001` 并拒绝消息；如果重复记录核对失败，则按数据库故障返回 `error/1005`，不会猜测为合法重试。

### 4.4 重复登录与连接状态

系统采用单会话策略。同一用户建立新连接时，Hub 原子替换在线及群组索引，并使用关闭码 4001 关闭旧连接；旧连接随后到达的注销事件只关闭自身，不会删除新连接。替换过程不广播下线和重新上线，只有首次连接和最终断开才通过 online_status 通知其他用户。

Client 的关闭操作是幂等的。Hub 不关闭发送 Channel，而是通过 Client Context、关闭控制帧和底层 Socket 结束读写协程，避免消息投递与 Channel 关闭并发时发生 panic。服务退出时，HTTP Server 与 WebSocket Hub 会在同一个超时窗口内关闭；Hub 会清空索引并主动关闭所有已接管的 WebSocket。

### 4.5 Redis 与消息队列基础

Redis 是后端启动依赖。服务会在启动时检查 Redis 连通性，超过 `redis.dial_timeout` 或连接失败时终止启动，避免应用在依赖不可用的状态下继续接收请求。HTTP Handler 不直接持有未使用的 Redis 客户端；后续缓存、限流或消息队列能力应通过职责明确的独立组件接入。

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| redis.key_prefix | chatroom | 隔离不同应用或环境的 Redis 键空间 |
| redis.dial_timeout | 5s | 建立连接和启动检查的超时 |
| redis.read_timeout | 3s | Redis 读取超时 |
| redis.write_timeout | 3s | Redis 写入超时 |
| redis.stream.chat_key | chatroom:stream:chat | 聊天消息流键名 |
| redis.stream.dead_key | chatroom:stream:chat:dead | 死信流键名 |
| redis.stream.group | chatroom-message-workers | 消费者组名称 |
| redis.stream.batch_size | 32 | 单次读取的最大消息数 |
| redis.stream.block_timeout | 1s | 阻塞读取等待时间 |
| redis.stream.claim_idle | 30s | 后续认领超时消息的空闲阈值 |
| redis.stream.max_length | 100000 | 后续限制消息流长度的目标值 |

`backend/internal/messagequeue` 定义了与 WebSocket 和具体中间件解耦的 `ChatMessage` 契约，以及只有一个 `Publish` 方法的发布接口。队列载荷使用带 `version` 字段的 JSON；当前协议版本为 1。编码和解码都会校验消息编号、发送者、接收目标、消息类型、内容和时间戳，未知协议版本会被明确拒绝。

`backend/internal/messagequeue/redisstream` 提供 Redis Streams 发布器与消费者。发布器校验并编码聊天消息，通过 `XADD` 向 `redis.stream.chat_key` 追加记录；每条记录包含 `msg_id` 和 JSON `payload`，并根据 `redis.stream.max_length` 使用近似长度限制。发布失败会保留底层 Redis 或 Context 错误，便于调用方判断和记录。

消费者通过 `XGROUP CREATE ... MKSTREAM` 从起始位置 `0` 幂等创建消费者组，再使用 `XREADGROUP` 和 `>` 批量读取尚未投递的新消息。消息经过解码和校验后交给单方法 `Handler`；只有 Handler 成功才执行 `XACK`。载荷损坏或 Handler 失败的消息保留在 Pending 中，读取或确认发生 Redis 故障时退出消费循环并向上层返回错误，Context 取消则正常结束。

WebSocket Hub 实现了消息队列 `Handler`。队列消息会先转换为现有 WebSocket 消息结构，再复用与原 Channel 入口相同的私聊或群聊处理函数。数据库写入和群成员解析成功后才实时投递并发送 `chat_ack`；数据库或成员解析失败会向消费者返回错误。相同 `msg_id` 的一致消息重复消费时只重新发送 ACK，不会重复写入记录或再次实时投递。

当前发布器和消费者尚未注入服务启动流程，因此运行中的私聊、群聊、消息持久化和 `chat_ack` 行为仍由原 Hub Channel 驱动。Pending 消息自动认领、有限重试和死信处理也尚未启用，应在切换现有消息入口前完成。

## 5. 数据模型

数据库初始化脚本位于 backend/scripts/init.sql。核心实体如下：

从包含已读回执和消息撤回功能的旧版本升级时，应先备份数据库，再在部署新版前执行 `backend/scripts/remove_optional_message_features.sql`。该一次性脚本会先删除原先处于非正常状态的消息，再移除 `messages.status` 列和 `read_receipts` 表；新建数据库只需执行 `init.sql`。

| 表 | 用途 | 关键字段或索引 |

| users | 用户身份与资料 | username 唯一索引、email 唯一索引、status |

消息接收目标使用两种类型：

- user：一对一会话，to_id 为对方用户 ID。
- group：群组会话，to_id 为群组 ID。

| role | 含义 |
| --- | --- |
| 0 | 普通成员 |

| 2 | 群主 |

### 6.5 消息与文件

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /api/v1/messages | 按目标、类型和分页查询历史消息 |
| POST | /api/v1/files/upload | 上传图片或文件 |
| GET | /api/v1/files/:file_id/download | 鉴权下载文件 |

历史消息查询示例：

~~~
GET /api/v1/messages?target_id=2&target_type=user&page=1&page_size=50
~~~

`target_type` 仅允许 `user` 或 `group`。历史消息分页中，`page` 默认为 1、有效范围为 1–10000；`page_size` 默认为 20、有效范围为 1–100。非法字符串、零、负数或超出上限均返回 `400/1001`。

WebSocket 重连后的增量补偿使用 `after_id` 游标：

~~~
GET /api/v1/messages?target_id=2&target_type=user&after_id=128&page_size=100
~~~

`after_id` 是上一轮响应中的 `next_cursor`，使用字符串表示，避免浏览器处理大整数时丢失精度。传入游标后，接口按消息数据库 ID 正序返回游标之后的消息，并通过 `has_more` 表示是否需要继续请求；下一页继续传入最新的 `next_cursor`。游标模式不能与 `page>1` 混用，非法游标返回 `400/1001`。普通分页响应同样携带当前结果的 `next_cursor`，前端据此初始化每个已加载会话的补偿位置。

查询群历史前会同时验证群组处于正常状态，并且当前用户是 `status=1` 的有效成员。群组已解散、用户不是成员或已经退出时统一返回 `403/1003`；数据库权限检查或消息查询失败时返回 `500/1005`，不会继续返回不完整的查询结果。

## 7. WebSocket 协议

### 7.1 建立连接

连接地址：

~~~
ws://localhost:8080/ws?token=token
~~~

浏览器 WebSocket 受限于无法自由添加 Authorization Header，因此服务端同时支持 Authorization Header 与 token 查询参数。前端在 HTTPS 页面会自动使用 WSS。

### 7.2 客户端事件

#### chat

~~~json
{
  "type": "chat",
  "data": {
    "msg_id": "59ffb838-6a50-4d9c-94e7-12cdd75269a1",
    "to_id": 2,
    "to_type": "user",
    "content_type": "text",
    "content": "你好，今天的评审准备好了吗？"
  }
}
~~~

content_type 支持 text、image、file；to_type 支持 user、group。

### 7.3 服务端事件

| type | 说明 |
| --- | --- |
| chat | 新的单聊或群聊消息 |
| chat_ack | 服务端确认消息已成功持久化并被接受处理 |
| online_status | 用户上线或下线状态 |
| error | 消息被拒绝或服务端无法完成处理 |

chat_ack 示例：

~~~json
{
  "type": "chat_ack",
  "data": {
    "msg_id": "59ffb838-6a50-4d9c-94e7-12cdd75269a1",
    "status": "sent"
  }
}
~~~

群消息会在进入 Hub 路由前检查群组状态和发送者的有效成员身份。群组不存在、已解散，或发送者不是有效成员时，服务端不会保存或转发消息，而是返回：

~~~json
{
  "type": "error",
  "data": {
    "code": 3001,
    "message": "群组不存在或无权发送消息",
    "msg_id": "59ffb838-6a50-4d9c-94e7-12cdd75269a1"
  }
}
~~~

如果消息进入 Hub 队列失败、接收成员查询失败或消息持久化失败，消息不会继续投递，发送者会收到错误码 `1005` 和对应的 `msg_id`，可以稍后重试。相同 `msg_id` 与已有消息冲突时返回 `1001`，客户端应生成新的消息编号，而不是继续重试原编号。收到 `chat_ack: sent` 表示服务端已经可靠写入消息或确认该消息此前已按相同内容写入；私聊接收者是否在线不影响这一确认。

前端发送消息后会先在当前会话中显示“发送中”，并等待对应 `msg_id` 的确认。收到 `chat_ack: sent` 后显示“已发送”；收到携带同一 `msg_id` 的 `error`，或 10 秒内没有收到确认时，显示失败原因和“重试”入口。一般失败会沿用原 `msg_id` 重试，以利用服务端幂等校验；错误码为 `1001` 时生成新的 `msg_id`，但仍更新原消息气泡，避免重复显示。页面卸载或连接被新会话替换时，仍在等待确认的消息会转为可重试状态。

### 7.4 连接关闭码

| code | 含义 | 前端行为 |
| --- | --- | --- |
| 1000 | 正常关闭 | 不影响主动断开流程 |
| 1001 | 服务端正在退出 | 保留自动重连，由退避策略等待服务恢复 |
| 1013 | 服务暂不可用或客户端消费过慢 | 保留自动重连 |
| 4001 | 当前账号连接已被新会话替换 | 停止自动重连并提示用户 |

4001 属于应用自定义关闭码。前端收到该关闭码后只停止当前页面的 WebSocket 重连，不清除 localStorage 中的 token，避免影响同一浏览器中的新会话。

## 8. 前端工作台

前端使用 Vue 3、Pinia、Vue Router、Axios 与 Element Plus，入口位于 frontend/src。

### 8.1 页面与状态

| 模块 | 责任 |
| --- | --- |
| Login / Register | 表单校验、注册登录、保存 token |
| User Store | 登录态、个人资料获取与退出 |
| Chat Store | 联系人、群组、当前会话、消息缓存、会话游标、增量补偿、投递状态、未读数和在线状态 |
| Chat View | 会话列表、历史与实时消息、重连补偿、发送状态与失败重试、群组详情、上传和资料编辑 |
| WebSocket Module | 建连、退避重连、重连成功事件、消息发送及 ACK、错误和超时状态管理 |

WebSocket 首次连接成功时不会触发历史补偿。连接异常断开并重新建立后，前端会并行同步已经加载过的会话：当前会话根据阅读位置决定是否自动滚动，其他会话把新增数量计入未读数。补偿消息按 `msg_id` 与实时推送去重；数据库中已经存在的本地失败消息恢复为“已发送”，真正未落库的失败气泡继续保留供用户重试。单个会话同步失败不会阻断其他会话。

### 8.2 前端代理与部署变量

开发服务器将以下路径代理到后端：

| 路径 | 用途 |
| --- | --- |
| /api | REST API |
| /ws | WebSocket |
| /static | 上传文件静态资源 |

部署时可使用以下前端变量：

| 变量 | 示例 | 用途 |
| --- | --- | --- |
| VITE_API_BASE_URL | https://example.com/api/v1 | API 地址 |
| VITE_WS_URL | wss://example.com/ws | WebSocket 地址 |

## 10. 部署建议与演进路线

### 10.1 生产部署建议

- 使用 HTTPS 与 WSS，并由反向代理统一处理证书、静态资源与长连接升级。
- 使用独立的生产数据库、Redis 实例与高强度 JWT 密钥。
- 将配置保留在部署环境中，仓库只维护 config.example.yaml。
- 为服务端添加运行指标、错误告警和访问日志归集。
- 涉及单会话关闭码时先发布前端或前后端同步发布，确保客户端能够识别 4001 并停止旧会话自动重连。

### 10.2 演进路线

1. 完善消息同步体验：离线消息拉取与会话排序。
2. 提升多人协作体验：更丰富的群组角色和通知策略。
3. 面向规模化部署：多实例 WebSocket 协同、消息分发与对象存储。
4. 提升工程质量：接口测试、并发测试、性能基线与持续集成。
